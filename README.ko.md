---

**문서는 계속 늘어나는데, 여전히 같은 방향을 바라보고 있을까요?**

프로젝트가 이어질수록 기획서, 구현 계획, API 안내, 운영 문서가 여러 폴더에 쌓입니다. 결정은 바뀌고 기능은 발전하지만, 모든 설명이 함께 바뀌는 것은 아닙니다. 문서 하나만 읽으면 맞는 말인데, 다른 문서와 나란히 놓으면 서로 다른 프로젝트를 설명하기도 합니다.

**Firecracker는 늘어나는 문서들이 프로젝트에서 합의한 방향을 여전히 따르고 있는지 확인하는 스킬입니다.** 문서의 주장을 기존 결정과 관련 구현에 연결해 어긋난 부분을 보여주고, 변경 전에 수정 계획을 검토할 수 있도록 돕습니다.

서로 다른 자리에서, 하나의 불꽃을 바라보다. 불꽃은 프로젝트에서 정한 방향이고, 각 문서는 자신의 역할과 관점을 유지합니다.

## 이럴 때 사용하세요

- 기능이 **A에서 A+로 바뀌었는데**, 영향받는 문서가 모두 갱신됐는지 불안할 때
- 여러 사람이나 코딩 에이전트가 다양한 폴더에 문서를 만들어 왔을 때
- 오랜만에 프로젝트를 다시 열어 어떤 문서가 현재 기준이고, 계획이고, 과거 기록인지 헷갈릴 때
- 인수인계나 배포 전에 서로 다른 지침과 변경 반영 누락을 확인하고 싶을 때
- 오래된 문서의 가치를 보존하면서 정리할 대상을 찾고 싶을 때

## 프로젝트의 방향은 사용자가 정합니다

Firecracker의 역할은 프로젝트에서 이미 내린 결정을 기준으로 문서의 일관성을 확인하는 것입니다. 문서 검사 과정에서 새로운 제품 방향, 아키텍처, 정책을 결정하지 않습니다.

| 이런 걱정이 들 수 있습니다 | 이를 줄이기 위한 동작 방식 |
| --- | --- |
| “내 프로젝트를 잘못 이해하면 어떡하죠?” | 판단 기준, 적용 범위와 원문 근거를 보여줍니다. 의도가 불명확하면 미해결로 보고하고 해당 내용은 그대로 둡니다. 실행 전에 사용자가 해석을 바로잡을 수 있습니다. |
| “잘못된 코드에 맞춰 올바른 문서를 바꾸지 않을까요?” | 합의된 요구사항과 실제 구현을 구분합니다. 구현 문제는 구현 문제로 보고하며, 요구사항을 약화하는 근거로 삼지 않습니다. |
| “모든 문서를 똑같이 만들지 않을까요?” | 문서의 역할, 환경 차이, 미래 목표와 과거 기록을 보존합니다. 같은 적용 범위에서 양립할 수 없는 주장만 충돌로 판단합니다. |
| “검사만 부탁했는데 파일이 바뀌나요?” | 기본 검사는 읽기 전용입니다. 결과와 제안을 먼저 보고하고, 구체적인 계획과 실행 허가를 바탕으로 변경합니다. |
| “오래된 문서가 사라지지는 않나요?” | 오래됐거나 링크·열람 기록이 없다는 이유만으로 삭제하지 않습니다. 정리 후보의 근거와 참조 영향을 설명하며, 삭제는 명시적인 허가가 필요합니다. |

이것은 완벽한 이해를 보장한다는 약속이 아니라 스킬이 따라야 할 작업 원칙입니다. 맥락을 놓치거나 근거를 잘못 해석할 수 있으므로, 판단은 사용자가 검토할 수 있는 제안으로 제시하고 불확실성과 미검토 범위를 공개합니다. 해결되지 않은 프로젝트 의도의 최종 판단은 사용자에게 있습니다.

**먼저 확인하고, 근거를 검토하고, 무엇을 바꿀지 결정하세요.** 처음부터 계획과 실행을 함께 요청했다면 허가된 범위에서 중복 확인 없이 진행합니다.

## 설치

### 터미널에서 설치

터미널에서 실행하세요. Node.js와 npm이 필요합니다.

```bash
npx skills add Yangms30/firecracker -a codex -g
```

`-a codex`는 Codex를 선택하고, `-g`는 모든 프로젝트에서 사용할 수 있도록 사용자 범위에 설치합니다. 현재 프로젝트에만 설치하려면 `-g`를 빼세요. 커뮤니티 [skills CLI](https://github.com/vercel-labs/skills#install-a-skill)를 사용합니다. Firecracker의 문서 목록 수집 스크립트를 실행할 때는 Python 3도 필요합니다.

### Codex 대화창에서 설치

또는 기본 스킬 설치기를 사용할 수 있는 **Codex 대화 입력창**에 아래 요청을 붙여넣으세요. 터미널 명령어가 아닌 설치 요청문입니다.

```text
$skill-installer https://github.com/Yangms30/firecracker 에서 Firecracker를 설치해줘.
SKILL.md는 저장소 루트에 있어. scripts/, references/, agents/, assets/도 함께 설치해줘.
```

## 검사 전후

**설명을 위한 예시:** 초안 생성 전에 사용자 승인이 필요하도록 결정이 바뀌었습니다. 업로드 단계의 자료 전처리는 여전히 허용됩니다.

| 문서 | 검사 전 | 승인된 수정 후 |
| --- | --- | --- |
| 승인된 기획서 | 승인 후에만 초안 생성 | 기준이 되는 결정으로 유지 |
| API 안내 | 업로드 즉시 초안 생성 시작 | 업로드는 자료 준비, 승인은 초안 생성 시작 |
| 운영 문서 | 업로드마다 초안 생성 재시도 | 승인된 생성 작업에 한해 재시도 |
| 과거 회의록 | 자동 생성 방식 제안 | 역사적 기록으로 보존 |
| 시각 디자인 가이드 | 글꼴과 간격 정의 | 유지; 승인 흐름을 추가할 필요 없음 |

**같은 방향이 같은 내용을 뜻하지는 않습니다.** 환경 차이, 미래 계획, 과거 기록은 서로 다른 내용을 담을 수 있습니다.

## 무엇을 검사하나요?

| 영역 | 확인할 수 있는 것 |
| --- | --- |
| 내용 충돌 | 같은 범위에서 양립할 수 없는 요구사항과 출처 |
| 변경 반영 누락 | 이전에 합의된 동작을 여전히 설명하는 문서 |
| 용어와 상태 | 바뀐 계약·명칭, 끊어진 참조, 완료된 것처럼 쓰인 제안 |
| 문서의 필요성 | 유지·수정·통합·보관·삭제 후보 제안 |
| AI의 열람 증거 | 제공한 로그에서 확인되는 열람·부분 열람·확인 불가 |
| 검사 범위 | 검토 완료·대기·부분 검토·차단·제외 파일과 탐색 경계 |

## 사용법

**검사 결과를 바탕으로 변경 계획 만들기**

```text
$firecracker 검사 결과를 바탕으로 파일별 변경 계획과 근거, 검증 방법을 작성해줘.
아직 파일은 수정하지 마.
불필요한 문서는 삭제 후보로 추천만 하고, 실제로 삭제하지는 마.
```

**합의된 변경을 따라가기**

```text
$firecracker 초안 생성이 업로드 즉시 자동 생성에서 사용자 승인 후 생성으로 바뀌었어.
영향받는 문서를 업데이트하고, 합의된 목표와 실제 구현 상태를 구분해줘.
```

**과거 코딩 에이전트의 열람 확인하기**

```text
$firecracker 이 코딩 세션 로그로 문서별 열람 증거를 확인해줘.
각 문서가 지금도 프로젝트에 필요한지는 별도로 평가해줘.
```

별도의 CLI 하위 명령어가 아닌 자연어 요청 예시입니다. 영어·한국어·중국어로 요청할 수 있으며, 보고서는 요청한 언어로 작성하고 수정할 문서는 원래 언어를 유지합니다.

**검토한 계획 실행하기**

```text
$firecracker 검토한 문서 변경 계획을 실행하고 결과를 검증해줘.
문서 삭제나 애플리케이션 코드 변경은 하지 마.
```

## 작동 방식

1. **전체 조사.** 문서 후보 수, 폴더 구조, 형식과 제외 범위를 파악합니다.
2. **역할 분류.** 경로와 이름으로 문서 역할을 추정하고 내용으로 확인합니다.
3. **구현 이해.** 진입점을 파악하고 관련 기능의 API·작업 큐·저장소·설정·테스트를 따라갑니다.
4. **내용 비교.** 확정된 결정, 현재 구현, 미래 목표와 과거 기록을 구분해 근거와 함께 비교합니다.
5. **최종 보고.** 파일을 수정하지 않고 문제·정리 제안·실제 문서 및 코드 검사 범위를 보고합니다.
6. **변경 계획.** 변경 요청을 받으면 파일별 수정 내용·의존 관계·검증 방법을 작성합니다.
7. **실행과 재검사.** 승인된 계획을 실행하고 관련 주제를 다시 검증합니다. 처음부터 계획과 실행을 함께 요청했다면 중복 확인 없이 진행합니다.

보고서에는 각 문제의 근거, 적용되는 결정, 제안하거나 수행한 조치, 판단의 확실성이 연결됩니다. 정리 후보에는 대체 문서와 영향을 받을 참조도 설명합니다.

## 한계

- 문서끼리 일치한다고 실제 구현까지 올바르다는 뜻은 아닙니다.
- 열람 기록은 이해나 준수를 증명하지 않습니다. 로그가 없으면 열람 여부는 확인 불가입니다.
- 오래됐거나, 링크가 없거나, 열람 기록이 없다는 이유만으로 삭제를 추천하지 않습니다.
- 기준이 되는 결정끼리 충돌하면 추가 근거나 결정이 나올 때까지 미해결로 남깁니다.
- 검사는 읽기 전용입니다. 일반적인 변경 요청에는 먼저 구체적인 계획을 작성합니다. 계획 승인 또는 명시적인 계획·실행 요청을 받으면 수정하며, 삭제에는 별도 명시적 허가가 필요합니다.
- 읽을 수 없는 파일과 미검토 구간을 포함해 실제 검사 범위를 공개합니다.
